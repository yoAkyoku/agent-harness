# Qwen3.5 9B：browser-01 與 search-01 的重複執行（2026-11-18）

## 目的

[browser-01](../qwen3.5-9b-browser-01-2026-11-18/README.md) 的 C 與 [search-01](../qwen3.5-9b-search-01-2026-11-16/README.md) 的 H 都只通過一次。一次通過不是成功率。這一批在 harness 不變的情況下（提交 `207e509` 的程式碼，另加錄影腳本的 `--temperature` 選項）重複執行，看這兩個結果有多穩定。

## 事先寫定的計畫（執行前寫入並提交）

溫度 0 時重複執行會重現同一個 Run（[hard-02 變異批次](../qwen3.5-9b-hard-02-variance-2026-11-16/README.md)已觀察到），所以重複主要在溫度 0.7 下進行。

- **browser-01**（[`scripts/record_real_model.py`](../../../../scripts/record_real_model.py)，時間上限 600 秒，與 C 相同）：
  - D：溫度 0，一次，看 C 能否重現。
  - E、F、G、H：溫度 0.7，各一次。
  - 通過條件與先前相同，寫在腳本說明裡：Run 以 `completed` 結束並保存一份成果。內容是否正確由人閱讀後記錄，不計分。
- **search-01**（`evaluation/run_suite.py evaluation/search-01 <輸出> --repeat 5 --temperature 0.7`）：三題各 5 次，共 15 次；評分條件是 `cases.json` 裡從第一批起就沒有改過的那一份。
- 所有執行都保留並計入，不重跑、不挑選；執行之後不修改評分條件。
- Ollama 在第一次執行前啟動，之後連續執行，所以只有第一次是冷啟動；時間只作參考。

## 觀察

1. **溫度 0 的單次結果是可重現的結果，不是一次抽樣。** D 和 C 完全相同，所以 C 的「通過」只說明這個設定下的那一條路徑會成功，不說明成功率。
2. **事先寫定的通過條件比任務本身寬。** 它要求 Run 完成並保存成果，harness 也確實驗證了每個引用都指向真實的證據；但 E、F 的成果只回答了任務的一部分，F 甚至寫「未提供」。驗證器依設計不讀任務文字，所以「引用都對」不等於「回答了問題」。要量內容，需要另一層知道任務的評分（例如逐項的 rubric），這一批沒有做。
3. **溫度 0.7 下，失敗的位置很分散**：工具誤用（F、H 對 Markdown 用表格工具）、輸出上限（G）、範圍外的來源（H）。只看溫度 0 看不到這些。
4. **兩次 `search-absent` 失敗直接來自保守的上下文上限。** 上限把每個 byte 當一個 token；以這次的任務文字為例，111 bytes 實際是 24 個 tokens（以釘選的 llama.cpp 分詞器計算），約 4.6 倍。G 則是輸出的保留空間（1,024 tokens）不夠；在 8K 視窗裡要多留輸出空間，也得先把輸入算準。下一個提交加入跨平台的精確計數，就是為了這一點。
5. H 先發布了一份不完整的成果，之後 Run 才失敗。已發布的成果會保留，這是發布的語意。錄影腳本會自動按下核准；實際使用時，核准卡片上的內容是使用者最後一次判斷內容是否完整的機會。
