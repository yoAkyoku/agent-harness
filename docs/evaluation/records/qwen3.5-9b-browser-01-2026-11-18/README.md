# Qwen3.5 9B 在工作台裡完成一個任務 browser-01（2026-11-18，兩次觀察）

## 目的

先前的評估都走 API 或無頭模式。這一批從瀏覽器操作工作台，和一般使用者一樣：載入範例資料、輸入任務、在需要時按下核准，並且全程錄影。目的是看到真實的本機模型在工作台裡實際的樣子，不是取得一個分數。

- 模型：`qwen3.5:9b-q4_K_M`（Ollama 0.40.10，digest `56671c2a…3c90`），`--decision-protocol json_tools`，依 README 的本機模型啟動方式。
- 任務（範例資料 `brief.md`、`metrics.csv`、`notes.md`）：「整理這個改版的目標、已知風險，以及三週訂單數的變化，存成一份附引用的摘要。」
- 開啟發布核准（預設）。錄影腳本：[`scripts/record_real_model.py`](../../../../scripts/record_real_model.py)。
- **事先寫定的通過條件**（寫在腳本的說明裡，執行前就已存在）：Run 以 `completed` 結束，並保存一份成果（這表示 harness 已驗證所有引用）。內容是否正確由人閱讀後記錄，不計分。
- 每次都是冷啟動：執行前才啟動 Ollama，模型尚未載入記憶體。

## 每一次發生了什麼

**A。** 模型的路線是對的：計畫（三步）→ 列出來源 → 一次讀取三份來源 → 用 `table_aggregate` 算出訂單總數與異常總數。接著在撰寫摘要的那一次模型呼叫中，Run 到達預設的 180 秒時間上限而結束。時間花在：

- **第一次模型呼叫 72 秒**：大部分是 Ollama 把 9B 模型載入記憶體，而這段時間算在 Run 的時間上限裡。
- 之後每次決策 5 到 62 秒。

這暴露了一個與任務無關的缺口：**工作台沒有地方可以調整時間上限**（只有無頭模式有 `--timeout-seconds`），而 180 秒對冷啟動的本機模型太短。修正是在「進階選項」加上時間上限（3、5、10 分鐘；伺服器原本就接受最多 600 秒），瀏覽器測試會檢查選擇的值確實送到伺服器。

**B。** 時間上限設為 10 分鐘，其他相同。這次第一次模型呼叫花了 110 秒，模型走得更遠：

1. 與 A 相同的計畫、列出與讀取，接著兩次 `table_aggregate`（E4 訂單 450、E5 異常 30）。
2. 一次 `number_calculate` 用了不存在的引數寫法（`E3_sum_exceptions`），被退回（`invalid_arguments`）；修正後算出異常率 6.666667%（E6）。
3. 寫出一份完整的摘要草稿。**內容是正確的**：目標、兩項已知風險、三週訂單數 120 / 150 / 180、總數 450、異常 30、異常率 6.67%、待確認事項，全部與來源一致；數字都引用了計算證據。
4. 但取自 `brief.md` 與 `notes.md` 的句子沒有在正文中引用，harness 依設計拒絕保存（`missing_body_citation`），並列出可用的引用格式。這已是最後一次修正機會（`remaining_corrections: 0`）。
5. 要讓模型修正，請求必須帶著整份草稿。harness 先依序省略了工具說明、結構描述、執行指引與成果名稱說明，仍然估計需要 8,402 tokens，超過 8,192 的保守上限，Run 以 `context_limit_exceeded` 結束。

## 結論

- 這個本機模型在這台機器上，可以在工作台裡做對任務的每一個實質步驟，包括正確使用計算工具；它沒有做到的是「每一句都附上引用」，而 harness 拒絕了沒有引用的成果，這是預期的行為。
- 在 8,192 tokens 的視窗裡，「三份來源加一份完整草稿再修正一次」放不下。這和 hard-02 `report-artifact` 的情況屬於同一類（見 [evaluation.md](../../../evaluation.md) 的 Known gaps）。可能的方向是讓修正請求只帶草稿中需要修改的部分，或在讀取後以 opt-in 的壓縮處理來源，這次都沒有做，也沒有再跑第三次。
- 冷啟動的載入時間算在 Run 的時間上限裡。另一個方向是在工作台啟動時預先載入模型，這次也沒有做。
- 兩次觀察都是單次結果，不代表成功率。
