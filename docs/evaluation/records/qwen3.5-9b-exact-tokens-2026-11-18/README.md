# Qwen3.5 9B：以精確 token 計數重跑（2026-11-18）

## 目的

[重複執行批次](../qwen3.5-9b-repeat-2026-11-18/README.md)中，`search-absent` 有兩次因 `context_limit_exceeded` 失敗，而保守的上限把每個 byte 當一個 token。提交 `7c8dae4` 加入跨平台的精確計數（`--exact-tokenizer-model`）。這一批只改這一件事，其他設定和重複執行批次相同，看結果有沒有不同。

## 事先寫定的計畫（執行前寫入並提交）

- **唯一的差別**：工作台加上 `--exact-tokenizer-model <Qwen3.5 9B 的 GGUF blob>`。溫度 0.7，時間上限、輸出保留（1,024 tokens）、修正與查找額度都不變。
- **search-01**：`evaluation/run_suite.py evaluation/search-01 <輸出> --repeat 5 --temperature 0.7 --exact-tokenizer-model <blob>`，三題各 5 次；評分條件不變。
- **browser-01**：`scripts/record_real_model.py <輸出> --channel msedge --time-limit 600 --temperature 0.7 --exact-tokenizer-model <blob>`，4 次（J1 到 J4）；通過條件不變，內容由人閱讀後記錄。
- **事先的預期**：`context_limit_exceeded` 應該不再出現，因為同樣的請求只算到約四分之一。其他種類的失敗（工具誤用、輸出上限、評分用詞）是模型的行為，不預期會改變。
- 所有執行都保留並計入，不重跑、不挑選。溫度 0.7 下每次抽樣都不同，5 次與 4 次只能看出大的差異；這一批不能證明成功率提高或降低。

## 結果

照計畫全部執行完畢（2026-11-18 下午，search-01 先、browser-01 後，連續執行），沒有重跑、沒有剔除。

### 計數本身

這一批共 116 次模型請求（search-01 91 次、browser-01 25 次）。**每一次**，harness 事先算出的提示 token 數都和 Ollama 事後回報的 `prompt_tokens` 完全相同；沒有任何一次觸發 `exact_context_mismatch`。最大的一次請求是 3,262 tokens，加上 1,024 的輸出保留，也遠低於 8,192 的視窗；search-01 的 91 次請求沒有任何一次需要裁切 Context；重複執行批次同樣的 search-01 有 65 次裁切。

計數本身每個 Run 花不到 0.1 秒。但 Run 變慢了：例如 `search-single` 從 11–19 秒變成 22–48 秒。時間幾乎都花在模型回應上（例如 search-single 第 1 次 46.7 秒中有 46.5 秒），最可能的原因是請求不再被裁切、提示變長，這台 8 GB 顯示卡的 prefill 變慢。這是保留更多 Context 的代價，這一批沒有進一步拆解。

## 觀察

1. **精確計數在真實請求上與 Ollama 完全一致**（116/116），這是比逐字串比對更直接的證據：比較的對象是模型伺服器實際處理的提示。
2. **預期的效果出現了**：Context 不再是 search-01 的限制，`context_limit_exceeded` 消失。但總分的變化（12→13、2→3）在 5 次與 4 次的樣本裡**不能當成改善的證據**，溫度 0.7 下單次結果本來就會變。
3. **新的限制浮現**：沒讀資料就寫「未提供」（J1、J4、先前的 F），以及核准後重複發布（J3）。這些是模型的行為，不是 Context 的問題；上下文變寬後，看得更清楚。
4. **代價是時間**：提示變長，模型回應變慢。若時間上限很緊，精確計數可能讓 Run 更容易超時；這一批的 600 秒上限沒有遇到。
5. 一個次要的發現：`source_too_large_for_context` 的拒絕訊息拿檔案的 bytes（15,901）和剩下的 tokens（5,318）比較。這是安全的方向（bytes 不會少於 tokens），但在精確計數下可能拒絕一份其實放得下的檔案，訊息裡的單位也混在一起。這次沒有修改。
