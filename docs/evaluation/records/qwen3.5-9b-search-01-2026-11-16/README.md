# Qwen3.5 9B 來源內搜尋 search-01（2026-11-16，六批）

## 目的

`source_search` 讓 Run 在已選來源內檢索相關的行（BM25，回傳帶行號的原文），不必整份讀取。這批用真實模型測三件事，都**不開啟壓縮**、來源都比上下文大（約 16 KB 對 8,192 token）：找一個事實、找分散在三處的三個事實，以及問一件來源裡沒有的事。

[`evaluation/search-01`](../../../../evaluation/search-01/cases.json) 定義三個任務，由 [`evaluation/run_suite.py`](../../../../evaluation/run_suite.py) 執行並自動評分。真值與評分條件在第一批執行前寫入 `cases.json`，五批之間**沒有修改**。

這份紀錄和先前的批次不同：它記錄的是一段開發過程。每一批實跑都暴露出 harness 的一個通用缺口，修正後再跑下一批。五批全部保留，各批的失敗都算數；最後一批不是「正確答案」，只是停止迭代的地方。

## 結果

| 批次 | harness 的變動（相對於前一批） | `search-single` | `search-scattered` | `search-absent` | 通過 |
|---|---|---|---|---|---|
| A | `source_search` 首次實跑 | 通過 | 失敗：`context_limit_exceeded` | 失敗：`context_limit_exceeded` | 1/3 |
| B | 放不進上下文的 `source_read` 會被拒絕；沒有匹配的搜尋成為可引用的證據 | 通過 | 失敗：`context_limit_exceeded` | **未通過評分**（Run 完成，見下） | 1/3 |
| C | 搜尋結果以剩餘空間為上限、匹配的行優先於相鄰行；相同的搜尋回傳同一筆證據 | 通過 | 通過 | 失敗：`step_limit_exceeded` | 2/3 |
| D | 相同的搜尋改為回傳「已經做過」的說明 | 通過 | 通過 | 失敗：`context_limit_exceeded` | 2/3 |

| F | 直接回答時在提示中列出可用的引用格式（稍後加入，見下） | 通過 | 通過 | 失敗：`correction_limit_exceeded` | 2/3 |

每批的完整事件在 `run-a` … `run-f`，各含三個 `.ndjson`、`results.json` 與 `summary.json`。

## 每一批發生了什麼

**A。** `search-single`：模型搜尋「結帳 中斷」，拿到 5 行、668 bytes，答對（第一次回答沒有引用，被退回後補上）。另外兩題，模型（直接，或在三次搜尋都沒有匹配之後）改用 `source_read` 讀整份日誌，請求超過上下文而停止。暴露的缺口：harness 明知這次讀取放不進去，仍然執行；而「搜尋不到」無法被引用，模型想誠實回答也沒有依據。

**B。** `search-scattered`：讀取被拒絕（`source_too_large_for_context`），模型改用搜尋，但查詢很寬（「服務中斷 週次 分鐘數 負責處理」，43 行匹配），回傳 59 行、7.7 KB，搜尋結果本身就超過了剩餘的 2.7 KB。`search-absent`：模型搜尋六次（其中三次是重複的查詢），然後回答：

> 根據提供的維運日誌來源（ops-log.md），文件中未出現「外洩」或相關關鍵字，因此無法確認有記錄資料外洩事件。[E1] [E2] [E3] [E4] [E5] [E6]

這個回答是誠實的，引用的是六筆「沒有匹配」的搜尋證據。但事先寫的評分條件只接受幾個否定詞（沒有、未記錄、未提及、未發現、查無、找不到、並無），不包含「未出現」「無法確認」，所以**依規則記為未通過**。條件沒有修改。

**C。** `search-scattered` 通過：43 行匹配中回傳 13 行、1.7 KB（含三個事件所在的行），三個事件全部答對。`search-absent`：相同的查詢現在回傳同一筆證據，模型在「外洩」與「洩漏」之間來回重複了 12 次，直到步數用完。上一批每次重複都拿到新的證據 ID，模型最後收尾了；去重之後它反而看不出自己在繞圈。**這個修正讓這一題變差。**

**D。** 重複的搜尋改為回傳一則「已經做過、結果不會變」的說明。模型沒有理會，繼續重複（中間試了一次新的字「洩密」），直到說明文字累積到超過上下文。

**E。** 重複的搜尋改為被拒絕並計入修正額度。這次模型的行為改變了：兩次被拒絕之後，它換了一個新查詢，然後寫出誠實的答案（「文件中未出現『資料外洩』、『外洩』或『洩漏』等關鍵字…無法確認」），但沒有附引用。答案被 `missing_answer_citation` 退回時，兩次修正額度已經被前面兩次重複搜尋用完，Run 以 `correction_limit_exceeded` 結束。9 次模型呼叫、23 秒，而不是繞到步數或上下文的上限。

**F。** 這一批是在 harness 加上「列出可用引用格式」的提示之後補跑的。`search-scattered` 這次第一個答案就附了引用（前三批都被退回一次）；`search-single` 仍被退回一次。`search-absent` 沒有改變：一次讀取被拒絕加上兩次重複搜尋被拒絕，就用完了修正額度，模型還沒走到回答那一步。

## 觀察

1. **找得到的東西，搜尋是無損而且便宜的做法**。`search-single` 五批都通過，每次 5 次模型呼叫；`search-scattered` 在 C 到 E 都通過，6 次模型呼叫。同樣的兩份日誌用壓縮（hard-02）要 8 到 9 次模型呼叫，而且模型讀到的是摘要；這裡模型讀到的是原文。
2. **「來源裡沒有」是這個模型用搜尋答不好的題目**，五批都沒有通過評分。只有 B 的 Run 完成並給出誠實的答案（但評分條件太窄）；E 的模型也寫出了誠實的答案，卻沒有修正額度可以補上引用。這題同時卡在三件事上：模型會重複查詢、它傾向不為「找不到」附引用、以及預設只有兩次修正。
3. **這個模型會對「被拒絕」做出反應，對「說明文字」不會**。讀取被擋、引用被退回、重複搜尋被拒絕，它每次都改變了做法；D 的說明文字放在成功的結果裡，它完全沒有理會。這是五批中最有用的發現，也是 E 的設計依據。
4. **一個修正可能讓另一題變差**（C 的去重）。只有每次修正後都重跑全部題目，才看得出來。
5. **保守的上下文上限是所有失敗的共同背景**。系統提示與工具目錄就佔了約 5,400 token，8,192 的視窗只剩不到 3 KB 給證據。這是以「每個 byte 至多一個 token」估算的結果，實際 token 數少得多。
6. **評分條件又一次比題意窄**（B 的 `search-absent`）。「否定詞清單」不是判斷誠實回答的好方法；下一個題組應該改成檢查「答案沒有宣稱某一週發生了該事件」，並人工確認。
7. **樣本很小**：三題、單一 9B 模型、溫度 0。五批之間的差異來自 harness 的變動，不是隨機性。

## 版本與設定

- Git 提交：A 到 E 是 `7b831e2` 之後的工作目錄，各對應上表所列的 harness 狀態，全部在提交 `8130508` 中加入，因此無法用單一提交重現 A 到 D 的行為；`8130508` 重現的是 E。F 是 `e6c1c31` 加上引用提示。
- 模型：`qwen3.5:9b-q4_K_M`，Ollama 0.40.10，JSON tools 協定，thinking 關閉，上下文上限 8,192 token
- 各 case 的旗標：`--answer --search`（沒有 `--compact`）
- 限額：每個 Run `max_steps` 14、`max_tool_calls` 24、`max_corrections` 2、`timeout_seconds` 420
- 執行方式：`uv run python evaluation/run_suite.py evaluation/search-01 <輸出資料夾>`
- D 的 `search-scattered` 花了 199 秒（其他批次約 30 秒），事件順序與 C、E 相同；原因沒有調查，推測是本機 GPU 當時被其他程式佔用。
